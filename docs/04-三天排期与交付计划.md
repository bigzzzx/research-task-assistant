# 科研计算任务助手三天排期与交付计划

建议把第二天结束时的目标定为“一次真实成功对话、一次真实失败对话，均可在界面重放工具记录”。第三天用来完成标黄加分项、从干净目录复现并录屏。考题从收到时起计 3 天，以下使用相对天数，实际截止时刻以收题时间为准。

本次开发先使用可控的模型流式响应完成联调。真实 DeepSeek 验收与录屏在配置 API Key 后进行。

## 一 开发顺序与每日完成条件

以下按一名开发者安排，工时是排期估算。测试随各模块编写，真实模型连通性在第一天检查。

| 时间 | 工作与依赖 | 当段结束时可检查的结果 |
| --- | --- | --- |
| 第 1 天上午，约 3 小时 | 评审口径确认后建立 Git 项目，按原文保留 `data/` 下三个样例。配置一个真实模型，先验证一次“请求工具 → 回填工具结果 → 流式回答”。编写共用 FASTA 校验与统计 | 保留一次真实模型往返记录。`seq_stats` 的正常值与基准一致，坏文件能同时报告两项错误 |
| 第 1 天下午，约 4 小时 | 完成 `find_orf` 与边界测试。建 SQLite 会话、消息、任务记录，接入后台工作线程和两路日志，实现三个工具 | 可在工具层拿到任务 ID、查运行中和两个终态、读取截断日志。两个脚本均能独立运行。先过 A02、A04、A07、A10 的脚本及工具部分 |
| 第 2 天上午，约 3 小时 | 接入手写 ReAct 循环，完善消息持久化、工具调用关联、任务完成后按原 ID 唤醒助手、失败主动读日志。接出 HTTP 与 SSE | 通过后端可以连续说“统计 sample1”“再对 sample3 做一次”。新任务沿用统计类型，能从日志解释两处错误 |
| 第 2 天下午，约 4 小时 | 完成侧栏、聊天输入和流式回复、工具卡、新建和切换会话。连接模型和真实子进程，修正顺序、恢复和归属问题 | 在浏览器用真实模型跑通 A01、A03，复核 A04、A05、A06。到这里应已具备必做主线的可录屏版本 |
| 第 3 天上午，约 3 小时 | 完成标黄加分项。先验证主动完成提示和切换会话、断线重连，再接入文件上传、重名处理和上传后的自然语言分析 | A08、A09 可演示。重新连接后结果可追溯，用户自己的文件走同一分析流程 |
| 第 3 天下午，约 4 小时 | 复核 A01–A13，补齐必要回归。换干净目录按 README 启动，检查 Git 历史和配置示例，录制 3–5 分钟成片，预留约 1 小时处理复现或录屏问题 | 留下实测版本、实际通过与未完成项，复播录屏，核对 `sample3`、工具返回和修正建议在画面中清晰可见 |

**排期取舍。** 正常目标是全部必做、主动通知、上传和关键逻辑测试。MCP 和 Docker Compose 是候补。若第二天的真实成功和失败对话还未跑通，第三天先修这两条路径并留出复现、录屏时间。加分项状态如实写入 README。评审前合适的简化是单后端进程、一个模型供应商、两个独立脚本。

## 二 先验证最容易拖延演示的事项

| 风险或依赖 | 尽早发现的方法 | 处理方式 |
| --- | --- | --- |
| 模型账号、地域端点或所选模型不支持所需组合 | 第一天用实际账号试一次流式工具调用和一次工具结果回传，记录模型 ID 和实测日期 | 从配置修改为账号可用且支持该能力的模型。受限期间可用可控替身开发界面与异常路径，交付前补真实模型验收 |
| 正确记录掩盖坏记录，或只显示首个错误 | 对源文件和改名副本运行两个脚本，检查退出码、stderr 和行号 | 校验完整文件并聚合问题，提交后实际运行脚本，再用失败轨迹核对回复 |
| 等待子进程卡住对话，或任务的完成消息串到别的会话 | 第一天记录提交与退出时刻，第二天交叉提交任务并切换到另一会话 | 后台独立等待子进程，所有完成事件携带原会话和任务 ID，按任务 ID 去重 |
| 自己电脑可用，评审者按 README 无法启动 | 第三天用干净目录、独立数据库和按说明填写的配置完整启动一次 | 锁定已验证的依赖，检查中文路径、端口、首次建库、模型配置和前端构建，以实测步骤修正 README |

## 三 交付包

1. **源码及提交历史。** 交付可访问的 GitHub/Gitee 仓库链接，或含源码且保留 Git 历史的压缩包。若选压缩包，可附可恢复历史的 Git bundle。建议按“分析脚本与样例”“异步任务与工具”“模型与前端”“验收与交付”形成可讲解的真实提交。
2. **README.md。** 写清已验证的运行环境和版本、依赖安装、环境变量示例、如何启动前后端、浏览器地址、样例的对话入口和测试命令。附整体架构图或文字，以及关键取舍、算法口径、已做和未完成部分。按评审者第一次打开项目的顺序编排。
3. **配置与样例。** 提供 `.env.example` 和三份内置 FASTA，写明如何取得并配置自己的模型凭证。提交前检查源码、Git 历史和录屏，确认真实 Key、用户上传文件、本地数据库和运行日志都未随包暴露。
4. **演示录屏。** 时长 3–5 分钟，使用真实模型、助手界面和本机子进程。`sample3` 的两条具体诊断及修正建议要能看清。建议同时展示工具卡和任务 ID，便于评审者对应实际行为。

## 四 约四分半钟的录屏脚本

| 时间 | 画面与动作 | 观众应看到什么 |
| --- | --- | --- |
| 0:00–0:25 | 打开本地页面，新建会话，展示三个样例文件名 | 助手处理的任务、输入位置和聊天入口 |
| 0:25–1:20 | “帮我统计一下 sample1 里序列的 GC 含量。”展开提交工具卡，保留输入框可用的画面 | 展示分析类型、文件名和任务 ID，随后自动展示状态、读日志的记录和两条统计结果 |
| 1:20–2:25 | 在同一会话紧接着说“再对 sample3 做一次”，不手动要求读日志 | 新 ID 对应 `sample3.fasta`，能看到失败状态、错误日志中的第 1 行和第 2 行，以及助手用通俗语言给出的修正建议 |
| 2:25–3:15 | 请求“找出 sample2 中每条序列最长的 ORF”，切换会话后再打开完成提示 | 后台继续运行，完成提示出现在原会话。`gene_A` 的坐标与长度和基准一致 |
| 3:15–3:55 | 从界面上传另一份合法 FASTA，直接引用上传文件做统计 | 文件名可辨认，三个原有工具处理用户文件，正常返回结果 |
| 3:55–4:25 | 刷新页面、切回原会话，展示历史工具卡，最后扫过 README 的启动和取舍段落 | 历史记录仍在，评审者知道如何复现。后端重启恢复另按 A05 实测 |

## 五 面谈准备与开工决策

复盘时从一次真实的 `sample3` 调用讲起。依次打开模型循环、任务记录、脚本校验和失败日志，说明第二条消息为什么沿用 `seq_stats`，以及模型如何得知两处错误。现场小改动可用“调整日志截断长度”作练习，定位 `read_log` 的参数并用 A07 复验。题面允许使用 AI 辅助现场修改。

| 本轮需要确认 | 建议默认值 | 影响 |
| --- | --- | --- |
| 首版功能 | 全部必做，优先主动通知和文件上传，配套关键测试 | 决定第三天的工作安排 |
| 实现选型 | React、FastAPI、SQLite、Python 子进程，默认模型为 DeepSeek Flash | 确定账号联通性检查、开发与启动方式 |
| 分析口径 | GC 采用确定碱基作分母。ORF 只取正链完整区间，1 基闭区间，包含终止密码子 | 决定四条合法输入记录和边界用例如何断言 |
