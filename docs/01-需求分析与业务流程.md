# 科研计算任务助手需求分析与业务流程

研究员在聊天窗口说“帮我统计一下 sample1 里序列的 GC 含量”，就应当能在自己的电脑上提交分析、继续对话，随后看到两条序列各自的结果。评审者可以展开工具记录，沿着同一个任务 ID 核对参数、状态、日志和助手的解释。这条路径，加上同一会话中对错误文件的处理，是本项目的首要交付。

**评审范围**　考题要求在收到题目后的 3 天内完成。应用的前端、后端、数据库和分析子进程都在本机运行。采用云端模型时，只有语言模型接口需要联网。题目鼓励使用 AI 编程工具，也要求提交者能在约 1 小时的复盘面谈中解释代码、现场修改。需求依据为考题第一至七节。[考题原文](<../智能体开发实践考题 (1).docx>)

## 一 用户和使用场景

| 使用者 | 要完成的事 | 可见的完成标志 |
| --- | --- | --- |
| 研究员 | 提交一个文件，查看进度，理解统计结果或失败原因 | 收到任务 ID，能继续发消息，看到与该文件匹配的结果，失败时知道该改哪一行 |
| 面试评审者 | 在自己的电脑上复现一次成功和一次失败，并核对实现 | 按 README 启动，能展开每次工具调用，对照样例核算结果，重启后找回同一段对话 |
| 项目开发者 | 在三天内做出能解释、能修改的实现 | 能独立讲清模型如何调用工具、脚本如何运行、失败如何回到聊天窗口 |

## 二 黄色标注如何影响范围

| 原文强调的内容 | 在考题中的性质 | 本次建议 |
| --- | --- | --- |
| 自然语言和它对话、运行序列分析任务、查询任务状态、读取日志并解释结果 | 项目主线，第二节列为必做 | 一次对话能走通提交、查询、读日志、解释。工具卡和后台任务使用同一 ID |
| `sample3` 的两类错误及修正建议，录屏中展示其失败处理 | 失败处理和录屏是必做，参考回复允许换措辞 | 保留坏样例原貌。验收时同时检查实际日志、助手答复、录屏画面 |
| 任务完成后主动通知前端 | 加分项，已标黄 | 优先纳入。研究员不必再发“完成了吗”，切到别的会话也能看到原会话有结果 |
| 在界面上传自己的 FASTA 文件 | 加分项，已标黄 | 纳入三天计划。上传成功得到可引用的文件名，分析沿用三个既有工具 |
| 分析脚本建议用 Python | 技术建议，语言和框架可自选 | 采用两个可单独运行的 Python 脚本，分别负责统计和 ORF 查找 |

其余加分项包括关键逻辑单元测试、用 MCP 封装三个工具并由后端作为 Client 调用，以及 Docker Compose 一键启动。建议首版配套关键测试，MCP 和 Compose 放在核心验收及录屏之后按余量决定；最终这三项均已完成，状态见 README。

## 三 必做需求与验收入口

| 编号 | 需求 | 验收看什么 |
| --- | --- | --- |
| R1 | 聊天窗口接受自然语言，助手文字随模型输出逐步显示。左侧可以新建和切换历史会话 | 回复结束前已有正文可见。新会话有独立上下文，切回旧会话能继续追问。见 A01、A05、A06 |
| R2 | 接入真实大模型，手写 ReAct 循环。模型发出工具调用，后端执行，结果回到模型，直至给出回答。题目允许厂商 SDK，明确排除直接套用 Dify、Coze 等低代码平台 | 能沿着一次真实会话找到模型的工具请求、对应返回和后续模型回复。见 A01、A03、A06 |
| R3 | 每次工具调用都展示工具名、实际参数、实际返回值，可以折叠 | 刷新前后都能核对同一组调用，失败时也能展开。见 A01、A03、A05 |
| R4 | 会话和消息存入数据库，浏览器刷新、后端重启后历史仍在 | 在两个会话分别发消息，刷新并重启，核对消息顺序、工具卡和任务归属。见 A05 |
| R5 | `submit_job` 按分析类型与文件名提交，立即返回任务 ID，后台异步执行。`job_status` 按 ID 查状态，至少有运行中、成功、失败。`read_log` 按 ID 读取标准输出和错误输出，过长时截断 | 脚本运行期间仍能对话。任务 ID 一路可核对，长日志有截断标记。见 A01、A03、A04、A07 |
| R6 | `seq_stats` 对每条序列给出 ID、长度、GC 含量。`find_orf` 对每条序列给出正链最长 ORF 的起止位置、长度。两个分析均由后端在本机以独立脚本子进程启动 | 用 `sample1` 和多行的 `sample2` 对照数值。两个脚本各自在内部延时 3–5 秒。见 A01、A02、A04 |
| R7 | 任务失败时，助手主动读日志，用普通人能懂的话说明原因并给出修正建议 | `sample3` 失败，出现 `read_log` 工具记录，回答指出缺少标题标记和非法字符，并告知如何修正后重提。见 A03 |
| R8 | 提交带 Git 历史的源码、能复现的 README 和 3–5 分钟演示录屏，录屏含 `sample3` 失败处理。密钥由环境变量或本地配置提供 | 评审者按说明配置自己的 Key 并启动，查看提交历史、成功与失败演示和已知取舍。见 A12 |

A01 等编号对应实际可操作的检查步骤和通过标准。[样例基准与验收用例](03-样例基准与验收用例.md)

## 四 端到端业务流程

**场景一　从一句话到两条统计结果。** 研究员新建会话，输入“帮我统计一下 sample1 里序列的 GC 含量”。助手把 `sample1` 对应到内置 `sample1.fasta`，调用 `submit_job(seq_stats, sample1.fasta)`。页面立即展示提交回执和 ID。后台完成后，助手用该 ID 调用 `job_status` 和 `read_log`，再流式回复每条序列的长度与 GC 百分比。研究员可在工具卡中核对原始数值。

**场景二　只换文件，沿用分析。** 在同一会话输入“再对 sample3 做一次”。助手从上一项明确的请求取到 `seq_stats`，为 `sample3.fasta` 创建新任务。脚本检查到首条记录缺失标题标记、第 2 行存在非法字符，任务失败。助手主动读新任务的错误日志，指出两处问题，建议补上 `>`、核对第 2 行的 `X` 和数字、保存后重提。文件末尾还有一条格式正确的记录，整份输入仍按失败处理。

**场景三　等待时继续工作。** 研究员询问“刚才的任务怎么样了”，助手调用 `job_status` 查询真实状态。研究员也可切换会话或提出新问题。任务完成时，当前会话收到结果，其他会话在侧栏显示提示，详情始终回到提交任务的会话。同一会话有多个候选任务且指代不清时，助手列出文件名和短 ID 请研究员选定。

**场景四　分析自己的文件。** 研究员通过聊天区的上传入口选取文件，看到系统登记的文件名，再要求“找这个文件里每条序列最长的 ORF”。助手沿用同一套提交流程。上传回执表示文件已接收，FASTA 内容由分析脚本校验，因此用户自己的坏文件也能得到逐行诊断。

## 五 评审时需要定下的口径

1. **交付优先级。** 建议先完成真实模型、两个脚本、工具记录、历史和失败诊断，再安排两项标黄加分功能。关键逻辑测试随实现一起编写。
2. **分析定义。** 建议正链三个阅读框都检查，只取有起始和同框终止密码子的完整 ORF。坐标从 1 开始、含两端，长度以核苷酸计并包含终止密码子。GC 的歧义碱基处理、并列 ORF 和无结果时的输出见验收文档。这些细则由项目约定，题面没有写死。
3. **模型和时间。** 首版采用 DeepSeek Flash。模型 ID 为 `deepseek-flash`，配置自己的 Key 后实测流式工具调用。三天按实际收题时刻计算，排期中的“第 1 天”由此起算。[DeepSeek 接入说明](https://api-docs.deepseek.com/zh-cn/)
